# MOOV Ops — Internal control

A single-page operations dashboard, fully internal. It draws on the same
underlying data as the Pepco client report but is not that report — every
page here carries carrier scorecards, booking rejections, named suppliers or
other detail that has no business reaching the client. If Pepco needs the
client report, that is a separate deployment (the `PEPCO-` repo); do not send
this URL.

Seven pages, ordered by where cargo is in the journey rather than by which
source extract a card came from:

| # | Page | What it answers |
| --- | --- | --- |
| 01 | **Act now** | What is overdue or urgent right now, ordered by consequence, with a drill-down by country, stage and supplier |
| 02 | **Origin** | Cargo-ready to vessel departure: our milestones, the client KPI steps, who is holding things up |
| 03 | **In transit** | What lands this week, how far the ETAs can be trusted, what is stuck at a transshipment port |
| 04 | **Destination** | The inbound workload, whether it landed on time, and the two places it stalls once it is in country |
| 05 | **Carriers** | League table, allocation compliance, rejected bookings |
| 06 | **Trends** | The longer view — weekly and monthly performance, volume, transit time |
| 07 | **Data & definitions** | What is not yet measurable, and what every figure on the page actually counts |

Where the client report and the internal extracts measured the same thing —
delivery performance, customs holds, coded cargo-ready reasons — the client
report's version is kept and placed alongside the internal detail on the same
page, rather than shown twice. Everything else keeps its place.

Everything is baked into `index.html`: markup, styles and the full dataset as
an inline `const D = {...}` object. There is no build step, no backend and no
runtime data fetching. The only external request is the Google Fonts
stylesheet.

## ⚠️ Before you share the link

This page carries internal operational data — named suppliers with their
overdue milestone counts, carrier scorecards, booking rejections, order IDs
and container numbers — and its own banner reads *"not for client
distribution."* Any host below serves it to anyone who has the URL, with no
login.

`robots.txt` and the `X-Robots-Tag` header ask search engines not to index it.
That keeps it out of Google; it does **not** make the link private. Delete both
if you want it indexed.

## Deploying

### Vercel

The repo is ready to import as-is — `vercel.json` marks it a static site.

1. <https://vercel.com/new> → **Import Git Repository** → pick this repo.
2. Framework preset: **Other**. Leave build command and output directory empty.
3. **Deploy**.

You get `<project>.vercel.app` in about a minute. Every later push to the
production branch redeploys automatically.

For a custom domain: Project → **Settings** → **Domains** → add it and point the
DNS record Vercel shows you at it.

### GitHub Pages

`.github/workflows/deploy-pages.yml` deploys on every push to `main` or
`claude/website-deployment-7u69nj`. Pages has to be switched on once by hand
first — the workflow's own token is not allowed to create the site:

1. **Settings → Pages → Build and deployment → Source: GitHub Actions**.
2. **Actions → Deploy to GitHub Pages → Run workflow** (or just push again).

The live URL — `https://b00817261-blip.github.io/PARI/` — then appears in the
workflow summary and under Settings → Pages.

Note that GitHub Pages is only free on public repos. If you make this repo
private, Pages needs a paid plan; Vercel serves private repos on the free tier.

## Updating the data

> **The 2026-08-23 refresh changed the shape of several exports.** The BI tool
> now delivers row-level detail (one row per order/booking) where it used to
> deliver pre-aggregated pivots. The scripts detect and handle both shapes — see
> **Export shapes** below — but two cards changed meaning as a result, and the
> page says so on the cards themselves.

`index.html` is generated by three scripts under `tools/`, run in order. Each
one is idempotent and reads the previous output before writing, so re-running
any of them alone is safe — but a full refresh from a clean folder of exports
is the three commands below:

```sh
pip install pandas openpyxl

# 1. page layout — only needed again if a page gains or loses a card
python3 tools/assemble.py --client ../pepco-/index.html \
  --internal <an internal-only index.html, see below> --out index.html

# 2. pages 01-06 (Act now's context strip, Origin's KPI steps, In transit,
#    Destination performance, Trends) — from the client-report exports
python3 tools/build_client_data.py ~/exports --write

# 3. the action queue, supplier league, Carriers, Data & definitions —
#    from the internal exports, most of which overlap with step 2's folder
python3 tools/build_dataset.py --src ~/exports --out D.json   # then re-inject D.json
```

Run them in that order — `build_dataset.py` owns the Definitions page and
needs the client figures already in place to describe both halves.

### Step 1: `assemble.py` — page layout

Rebuilds `index.html` from two source files: the Pepco client report
(`--client`) and an internal-only build (`--internal`) that has the same nine
pages this dashboard used to carry as a flat block. It lifts each card out of
whichever source has the better version, places it on its journey-ordered
page, and wires the internal JS (the action queue, the country/stage/supplier
drill-down, the stage strip, KPI bars, carrier league, definitions) on top of
the client file's stylesheet and raw-table widget — both are the better of the
two. You only need to re-run this if the *set of cards* changes, not for a
routine data refresh.

### Step 2: `build_client_data.py` — client-sourced pages

Builds the client-report figures from eleven exports, matched on a filename
fragment so the BI tool's random prefix does not matter:

| Export | Feeds |
| --- | --- |
| `latest_delivery_da…` | Destination performance, Origin due-at-DC window, Trends monthly on-time, transit *(shared with step 3)* |
| `PO_milestone_performance` | Origin's coded cargo-ready reasons *(shared with step 3)* |
| `supplier_performance_2` | supplier names on Destination performance and Act now's needs-attention list |
| `AHOD_reason_code_2` | miss reasons, FM events, the S01 exclusion |
| `destination_milestone` | In transit arrivals this week |
| `transport_carrier` | Act now's context strip (deliveries into DCs today) |
| `pepco_tranship_port_performance` | In transit's transshipment waiting card |
| `Monthly_Summary` | Trends monthly TEU volume |
| `destination_lead_time_analysis` | Trends port-to-DC final leg |
| `customs_clearance_finished` | Destination's customs held card *(optional)* |
| `predictive_eta` | In transit's ETA reliability bars *(optional)* |

`customs_clearance_finished`, `predictive_eta`, `PO_milestone_performance` and
`Monthly_Summary` are optional. If they are absent the build keeps those cards'
previous figures, prints them under **NOT UPDATED**, and the page labels each
affected card with the extract date it is still showing — so nothing stale
reads as current. Everything else is required and the build stops if it is
missing.

### Step 3: `build_dataset.py` — internal-sourced pages

| Export | Feeds |
| --- | --- |
| `PO_milestone_performance` | Origin's stage strip, Act now's action queue, supplier league *(shared with step 2)* |
| `latest_delivery_data__pepco` | stale tracking records, data-quality counts |
| `demurrage__detention_tracker` | Destination's demurrage card |
| `booking_rejection_analysis` | Carriers' rejections card |
| `pepco_carrier_scoring` | Carriers' league table |
| `carrier_performance` | Carriers' ETD slip column |
| `OHA_KPI` + `pepco_weekly_volume` | Origin's KPI bars, weighted by shipments |
| `shipping_document_verification` | Origin's doc-verification card |

Then paste the contents of `D.json` over the `const D = {...}` literal at the
bottom of `index.html`. Both hosts redeploy on push, and `index.html` is served
`must-revalidate` so viewers pick up the new numbers without a hard refresh.

This script also measures the definitions it applied — window widths, due-date
coverage, and how well each stage's own dates reproduce the segment the export
assigns — and writes them into `D.defs`, which renders as **Data &
definitions**. That page is generated, not hand-written, so it always
describes the refresh currently deployed.

### As-of dates

The as-of date is taken from the data (`max ATA`), not passed in as an
argument. When both builds run from the same folder they land on the same
date and the header shows one; if a refresh leaves them a day apart the header
shows both, and the Definitions page adds a caveat explaining which pages come
from which extract and that they will not reconcile exactly.

### Export shapes

Three exports arrive in a different shape since 2026-08-23. Each script sniffs
the columns and takes the matching path, so both the old and new shapes build.

| Export | Was | Now | Effect |
| --- | --- | --- | --- |
| `tranship_port_performance` | pre-aggregated, with `Count of Container` | one row per booking, raw `ATA`/`ATD` in the transit port | **The card counts bookings, not containers** — the new export carries no container count. Its labels were changed to match. Dwell is measured per booking. |
| `OHA_KPI` + `pepco_weekly_volume` | week-blocked pivot of rates, weighted by weekly shipments | one row per order, `Ontime`/`Not Ontime` per step, split across `origin_oha_*.xlsx` + a global `origin_kpi_report*.xlsx` | **Five KPI steps instead of thirteen.** Only steps present unambiguously in both shapes are carried; the rest have no verdict column and are dropped rather than guessed at. Counted per order, so no weighting is needed. |
| `supplier_performance` | — | unchanged shape, but truncated at 150,000 rows | Overlaps `latest_delivery_data` (also truncated) on only ~59% of orders, so 4 in 10 delivery rows show no supplier name. |

The row-level origin exports must be named `origin_oha_<CC>.xlsx` (one per
country) and `origin_kpi_report*.xlsx` (the global one). Country files are
treated as complete for their country; the global file is truncated, so it only
fills in orders the country files do not already hold. Deduplication is on
`Order Number`.

### When an export is missing

`PO_milestone_performance` and `Monthly_Summary` are no longer fatal. If either
is absent the build keeps the previous figures for everything it feeds and adds
a `not_updated` entry, which renders as a red *"Not refreshed — still the
&lt;date&gt; extract"* line on each affected card. Currently that covers:

| Missing export | Cards held back |
| --- | --- |
| `PO_milestone_performance` | Act now's action queue, Origin's stage strip, the supplier league, coded cargo-ready reasons |
| `Monthly_Summary` | Trends monthly TEU and volume |
| `customs_clearance_finished` | Destination's customs held card |
| `predictive_eta` | In transit's ETA reliability bars |

`Monthly_Summary` has no substitute in the current set: the booking-level
`weekly_closing.xlsx` export carries TEU and containers but **no order count**,
and the volume card plots all three. Swapping a booking count in for an order
count would change what the series means, so the whole card is held instead.

### Things the scripts cannot do for you

- **Allocation compliance** has no export in the current set, so the internal
  build carries the previous values forward and the Carriers card is labelled
  with its own older date. Supply a nomination/booked TEU export to make it
  live.
- **The row cap.** The milestone and delivery exports come out of BI capped at
  150,000 rows with *"some data may have been omitted"* in the footer. The
  script reads that footer and surfaces it on Data & definitions. Raise the
  export limit before anyone quotes these counts as totals.
